### 🐍 CHAPTER 1: Python for AI — Q&A

**Q1. What is the difference between a generator and an iterator in Python?**
> An **iterator** is any object with `__iter__()` and `__next__()`. A **generator** is a function using `yield` that creates an iterator lazily — values are computed on demand, so memory usage is O(1) vs O(n) for lists. Critical for processing large datasets that don't fit in RAM.

**Q2. How do Python decorators work? Give an ML use case.**
> A decorator wraps a function to add behavior without modifying it. Implemented as a function that takes a function and returns a new function. ML use case: timing training steps, caching expensive feature computations, logging model predictions for monitoring.

**Q3. What is the GIL and why does it matter for ML?**
> The Global Interpreter Lock (GIL) allows only one thread to execute Python bytecode at a time. For CPU-bound ML workloads, use `multiprocessing` (separate processes, no GIL) instead of `threading`. For I/O-bound work (data loading), `asyncio` or `threading` is fine. PyTorch releases the GIL during C++ operations — that's why it can do true parallelism.

**Q4. How does NumPy vectorization outperform Python loops?**
> NumPy operations run in C under the hood, use contiguous memory (cache-friendly), SIMD instructions (process multiple elements per CPU cycle), and avoid Python object overhead. A vectorized operation on 1M elements can be 100–500× faster than a Python for-loop.

**Q5. What is `__slots__` and when would you use it in ML code?**
> `__slots__` prevents dynamic attribute creation, storing attributes in a fixed array instead of a dict. Reduces memory per object by ~40–60%. Useful when creating millions of lightweight objects (data points, feature vectors) in a custom dataset class.

**Q6. Explain `asyncio` and when you'd use it in an AI system.**
> `asyncio` enables single-threaded concurrency using an event loop. Ideal for I/O-bound tasks: calling LLM APIs concurrently, streaming model responses, fetching batch embeddings without blocking. Use `async def` + `await` for async functions, `asyncio.gather()` for parallel I/O.

**Q7. What is the difference between `deepcopy` and `copy`?**
> `copy.copy()` creates a shallow copy — nested objects share references. `copy.deepcopy()` recursively copies all nested objects. In ML: always deepcopy model weights before fine-tuning if you want to keep the original; shallow copy of a model shares parameter tensors.

**Q8. How does Python manage memory? What are common memory leaks in ML code?**
> Python uses reference counting + cyclic garbage collector. Common ML leaks: (1) holding references to tensors in lists during training loop — use `tensor.item()` for scalars, (2) not clearing gradient graph — call `loss.backward()` then `optimizer.zero_grad()`, (3) dataset objects holding file handles. Profile with `tracemalloc` or `memory_profiler`.

### 🧮 CHAPTER 2: ML Fundamentals — Q&A

**Q9. Explain the bias-variance trade-off.**
> **Bias** = error from wrong assumptions (underfitting — model too simple). **Variance** = error from sensitivity to training data (overfitting — model too complex). Total error = Bias² + Variance + Irreducible noise. High bias → increase model complexity or add features. High variance → more data, regularization, dropout, early stopping. The trade-off: reducing one often increases the other.

**Q10. What is regularization? Explain L1 vs L2.**
> Regularization adds a penalty to the loss to prevent overfitting. **L1 (Lasso)**: adds `λ|w|` — produces **sparse** weights (drives some to exactly 0), useful for feature selection. **L2 (Ridge)**: adds `λw²` — shrinks all weights toward 0 but rarely to exactly 0, better when all features matter. **Elastic Net**: L1 + L2 combined.

**Q11. When would you use precision vs recall vs F1?**
> **Precision** = TP/(TP+FP) — "Of predicted positives, how many are correct?" Use when false positives are costly (spam detection — don't block real email). **Recall** = TP/(TP+FN) — "Of actual positives, how many did we catch?" Use when false negatives are costly (cancer detection — don't miss a case). **F1** = harmonic mean — use when you need balance. **AUC-ROC** — use for ranking/threshold-independent evaluation.

**Q12. Explain cross-validation and why k-fold is better than train/test split.**
> K-fold splits data into k folds, trains on k-1, tests on 1, repeats k times, averages results. Benefits: uses all data for both training and validation, gives variance estimate of model performance, less dependent on a single lucky/unlucky split. Use **stratified k-fold** for imbalanced classes. Downside: k× training cost.

**Q13. What is the difference between bagging, boosting, and stacking?**
> **Bagging** (Bootstrap Aggregating): train multiple models on random data subsets in parallel, average predictions → reduces variance. Example: Random Forest. **Boosting**: train models sequentially, each focusing on previous errors → reduces bias. Examples: XGBoost, LightGBM, AdaBoost. **Stacking**: use a meta-model to learn how to combine base model predictions → can capture what no single model gets right.

**Q14. How do you handle class imbalance?**
> (1) **Resampling**: oversample minority (SMOTE) or undersample majority. (2) **Class weights**: pass `class_weight='balanced'` — penalizes misclassifying minority class more. (3) **Threshold tuning**: lower decision threshold for minority class. (4) **Metrics**: use F1, AUC-ROC, or AUC-PR instead of accuracy. (5) **Ensemble methods**: BalancedBaggingClassifier. Best practice: try class weights first (no data loss), SMOTE if still poor recall.

**Q15. Explain gradient descent variants: SGD vs Mini-batch vs Adam.**
> **SGD (full batch)**: uses all data per step — stable but slow and memory-heavy. **Mini-batch SGD**: uses a small batch — good balance of speed and stability. **Adam**: adaptive learning rates per parameter (uses first + second moment estimates), combines momentum and RMSprop → converges faster, less sensitive to learning rate. Default for most deep learning. Use SGD with momentum for final fine-tuning of large models (often generalizes better than Adam).

**Q16. What is data leakage and how do you prevent it?**
> Leakage = information from test/future data leaks into training → inflated metrics, fails in production. Types: (1) **Target leakage** — feature computed after the event you're predicting. (2) **Train-test leakage** — preprocessing (scaling, encoding) fitted on all data before splitting. (3) **Temporal leakage** — using future data to predict the past. Prevention: always split first, then fit preprocessors only on training data (use `sklearn` Pipeline).

**Q17. How does a Random Forest work? What are its hyperparameters?**
> Builds many decision trees on bootstrap samples with random feature subsets at each split (feature bagging). Final prediction = majority vote (classification) or average (regression). Key hyperparameters: `n_estimators` (more = better, diminishing returns), `max_depth` (controls overfitting), `max_features` (sqrt(n) for classification, n/3 for regression), `min_samples_leaf`. Feature importance = mean decrease in impurity across all trees.

**Q18. What is the curse of dimensionality?**
> As dimensions increase, data becomes sparse — distance metrics lose meaning (all points equidistant), volume grows exponentially so you need exponentially more data to cover the space. Manifests as: KNN fails, clustering becomes harder, overfitting increases. Solutions: PCA/t-SNE for dimensionality reduction, feature selection, regularization, embedding layers in deep learning.

### 🧠 CHAPTER 3: Deep Learning & Neural Networks — Q&A

**Q19. Explain backpropagation mathematically.**
> Backprop computes gradients of the loss w.r.t. all parameters using the chain rule. Forward pass: compute activations layer by layer. Backward pass: compute `∂L/∂W` for each layer using `∂L/∂W_l = ∂L/∂a_l × ∂a_l/∂z_l × ∂z_l/∂W_l`. The chain rule connects these: `∂L/∂W_l = δ_l × a_(l-1)^T` where `δ_l = (W_(l+1)^T × δ_(l+1)) ⊙ σ'(z_l)`. Updates: `W = W - lr × ∂L/∂W`.

**Q20. What is the vanishing gradient problem and how is it solved?**
> In deep networks, gradients shrink exponentially as they backpropagate through sigmoid/tanh activations (derivatives < 1). Early layers learn extremely slowly or not at all. Solutions: (1) **ReLU** — gradient is 1 for positive inputs (no squashing). (2) **Batch Normalization** — normalizes activations, prevents extreme values. (3) **Residual connections (ResNet)** — skip connections provide gradient highways. (4) **Gradient clipping** — for RNNs. (5) **LSTM gates** — learned control of gradient flow.

**Q21. Explain the Transformer architecture in detail.**
> Transformer = stack of encoder/decoder blocks (GPT uses decoder-only). Each block: (1) **Multi-Head Self-Attention**: `Attention(Q,K,V) = softmax(QK^T/√d_k)V` — queries attend to all keys, weighted sum of values. Multiple heads capture different relationship types. (2) **Add & Norm**: residual connection + LayerNorm. (3) **Feed-Forward Network**: 2-layer MLP applied position-wise. (4) **Positional Encoding**: sine/cosine or learned embeddings (no recurrence — position must be injected). Input tokens → embeddings → N blocks → output logits.

**Q22. What is the difference between BERT and GPT?**
> **BERT** (encoder-only): bidirectional attention — each token attends to all others. Trained with Masked Language Modeling (MLM) + Next Sentence Prediction. Best for: classification, NER, QA, embeddings. **GPT** (decoder-only): causal/autoregressive attention — each token attends only to past tokens. Trained with next-token prediction. Best for: text generation, completion, few-shot learning. **T5** (encoder-decoder): for sequence-to-sequence tasks (translation, summarization).

**Q23. Explain attention mechanism — why does it work?**
> Attention lets each position in a sequence directly attend to all other positions, computing a weighted sum of values where weights reflect relevance. Unlike RNNs (sequential, fixed hidden state), attention captures long-range dependencies in O(1) steps. Scaled dot-product: `softmax(QK^T/√d_k)V`. Scaling by √d_k prevents gradients vanishing in softmax when d_k is large. Multi-head: different heads learn different types of relationships (syntax, coreference, semantics).

**Q24. What are common training tricks for deep learning?**
> (1) **Learning rate scheduling**: warmup + cosine decay — prevents early instability, improves final performance. (2) **Gradient clipping**: `clip_grad_norm_()` — prevents exploding gradients in RNNs/Transformers. (3) **Batch Normalization**: stabilizes training, allows higher LR. (4) **Dropout**: randomly zero activations — forces redundant representations. (5) **Mixed precision (fp16/bf16)**: 2× memory reduction, 2-3× faster on A100. (6) **Data augmentation**: prevents overfitting by increasing effective dataset size. (7) **Early stopping**: stop when val loss stops improving.

**Q25. What is BatchNorm and why does it help?**
> BatchNorm normalizes activations within a mini-batch: `z = (x - μ_batch) / σ_batch`, then scales and shifts with learned γ, β. Benefits: (1) Reduces internal covariate shift — each layer sees stable input distribution. (2) Acts as regularization (adds noise via batch statistics). (3) Allows much higher learning rates. (4) Reduces sensitivity to initialization. At inference: uses running mean/variance computed during training (not batch stats).

**Q26. Explain CNNs — how do convolutions work?**
> A convolution slides a filter (kernel) across the input, computing dot products to produce a feature map. Key properties: (1) **Local receptive field** — each filter responds to a small patch. (2) **Weight sharing** — same filter applied everywhere → fewer parameters, translation invariance. (3) **Hierarchical features** — early layers: edges/textures; deep layers: objects/faces. Pooling (max/avg) reduces spatial size, adds translation invariance. Common architectures: VGG (deep, simple), ResNet (skip connections), EfficientNet (compound scaling).

**Q27. When would you use an LSTM vs a Transformer?**
> **LSTM**: sequential processing, handles variable-length sequences, memory-efficient for very long sequences (linear complexity). Good for: time-series, streaming data, edge devices. **Transformer**: parallel processing (faster training), better at capturing long-range dependencies, scales better with data and parameters. Quadratic attention complexity (O(n²)) — problematic for very long sequences (use Longformer, FlashAttention, or Mamba for long contexts). In 2024+: Transformers dominate; LSTM mainly for constrained/streaming settings.

### 🤖 CHAPTER 4: LLMs & GenAI — Q&A

**Q28. Explain how GPT is trained (pre-training + fine-tuning).**
> **Pre-training**: next-token prediction on massive text corpus (Common Crawl, Wikipedia, Books). Model learns language, facts, reasoning implicitly. **Supervised Fine-Tuning (SFT)**: train on curated instruction-response pairs — teaches the model to follow instructions. **RLHF**: (1) train a Reward Model on human preference comparisons; (2) use PPO to optimize LLM output to maximize reward while staying close to SFT model (KL divergence penalty). **Alignment = SFT + RLHF** makes the model helpful, harmless, honest.

**Q29. What is RAG (Retrieval-Augmented Generation) and when do you use it?**
> RAG = retrieve relevant documents from a knowledge base + inject them into the LLM prompt as context. Architecture: (1) **Indexing**: chunk documents → embed with encoder → store in vector DB (Pinecone, Chroma, FAISS). (2) **Retrieval**: embed query → cosine similarity search → retrieve top-k chunks. (3) **Generation**: prompt = system + retrieved chunks + user query → LLM generates answer. Use RAG when: knowledge changes frequently (avoid retraining), domain-specific facts needed, need citations/grounding, context fits in window. Use fine-tuning when: style/format/behavior change needed, latency-critical (no retrieval step).

**Q30. What is LoRA and why is it important?**
> **LoRA (Low-Rank Adaptation)**: instead of fine-tuning all parameters, add small trainable rank-decomposition matrices to attention layers: `W' = W + BA` where B ∈ R^{d×r}, A ∈ R^{r×k}, r << d. Only B and A are trained (0.1–1% of parameters). **QLoRA**: quantize base model to 4-bit (NF4), add LoRA adapters in fp16 → fine-tune 65B model on a single A100. Benefits: 90%+ memory reduction, comparable quality to full fine-tuning, swappable adapters per task. Used by: Alpaca, Vicuna, most open-source LLM fine-tunes.

**Q31. How do you prevent LLM hallucination in production?**
> (1) **RAG** — ground responses in retrieved facts, add citations. (2) **Constrained generation** — force JSON output, validate schema. (3) **Self-consistency** — sample multiple responses, take majority vote. (4) **Chain-of-Thought prompting** — "think step by step" reduces errors on reasoning tasks. (5) **Constitutional AI** — self-critique and revision. (6) **Guardrails** — NeMo Guardrails, LlamaGuard for safety/factuality filtering. (7) **Temperature = 0** for factual tasks. (8) **Retrieval + verification** — cross-check claims against knowledge base.

**Q32. Explain the difference between zero-shot, few-shot, and fine-tuning.**
> **Zero-shot**: prompt with instruction only, no examples → "Classify sentiment: 'Great product!'" **Few-shot**: include k examples in prompt → model infers pattern. Works for GPT-4 level models. **Fine-tuning**: update model weights on task-specific data → best quality, requires data + compute, changes model behavior permanently. **When to use**: zero-shot for general tasks, few-shot for uncommon formats, SFT when zero/few-shot quality is insufficient, LoRA for domain adaptation with limited budget.

**Q33. What is prompt engineering? Key techniques?**
> Crafting inputs to elicit optimal LLM outputs without changing weights. Key techniques: (1) **Role prompting**: "You are an expert data scientist..." (2) **Chain-of-Thought (CoT)**: "Let's think step by step" → improves reasoning on math/logic. (3) **Few-shot examples**: show input-output format. (4) **Output formatting**: "Respond only in JSON with keys: category, confidence" (5) **Self-Ask**: "What do I need to know to answer this?" (6) **ReAct**: Reason + Act — interleave reasoning steps with tool calls. (7) **Tree of Thoughts**: explore multiple reasoning paths.

**Q34. What is an AI agent? How do you build one?**
> An agent = LLM + tools + memory + planning loop. The LLM decides which tool to call, observes result, reasons next step. Architecture: (1) **Tools**: functions the LLM can call (web search, code executor, database query, calculator). (2) **Memory**: short-term (conversation history), long-term (vector store of past interactions). (3) **Planning**: ReAct loop — Reason → Act → Observe → repeat until goal met. Frameworks: LangChain Agents, LlamaIndex, AutoGen (multi-agent), CrewAI. Production considerations: tool timeout, max iterations, sandboxed code execution, human-in-the-loop for high-stakes actions.

**Q35. How does RLHF work? What are its failure modes?**
> **Step 1 — SFT**: fine-tune on human-written responses. **Step 2 — Reward Model**: train a classifier on human comparisons (response A vs B), learns a scalar reward. **Step 3 — PPO**: optimize LLM with policy gradient to maximize reward while KL-diverging from SFT model (prevents reward hacking). Failure modes: (1) **Reward hacking** — model finds ways to get high reward without being helpful (e.g., very long answers). (2) **Reward model overfit** — RM doesn't generalize. (3) **Mode collapse** — model loses diversity. (4) **Human annotator bias** — RM inherits annotator preferences. Mitigations: KL penalty, diverse annotators, iterative refinement (Constitutional AI).

**Q36. Explain vector databases. When do you use FAISS vs Pinecone?**
> Vector DBs store high-dimensional embeddings and support approximate nearest neighbor (ANN) search. **FAISS** (Facebook AI Similarity Search): open-source, runs in-memory or on disk, supports GPU, index types: Flat (exact), IVF (inverted file, fast), HNSW (graph-based, best accuracy/speed trade-off). Use for: self-hosted, cost-sensitive, batch search. **Pinecone**: managed cloud service, real-time upserts, metadata filtering, horizontal scaling, SLA. Use for: production RAG where you need managed infra, real-time updates, team without MLOps expertise. **Chroma**: lightweight, open-source, good for local dev/prototyping.

**Q37. What is FlashAttention and why does it matter?**
> Standard attention materializes the full N×N attention matrix (O(N²) memory). **FlashAttention**: IO-aware exact attention — computes attention in tiles, uses GPU SRAM (fast) instead of HBM (slow), never materializes full matrix → O(N) memory, 2–4× faster, same output as exact attention. Critical for long-context models (128K+ tokens). FlashAttention-2 adds parallelism across sequence length. Most frontier models (GPT-4, Llama, Claude) use it. As an AI engineer, know this is the reason long-context models became practical.

**Q38. What is quantization in the context of LLMs?**
> Reducing model weight precision from fp32/fp16 to int8/int4 to reduce memory and increase inference speed. Types: (1) **Post-Training Quantization (PTQ)**: quantize after training, fast, slight quality loss. (2) **Quantization-Aware Training (QAT)**: simulate quantization during training, better quality. Methods: **GPTQ** (weight-only, round-to-nearest per layer), **AWQ** (activation-aware, preserves salient weights), **NF4** (QLoRA's normal float 4-bit, best for fine-tuning). Trade-off: 4-bit ≈ 4× memory reduction, ~1–3% quality loss on benchmarks.

### 🏗️ CHAPTER 5: ML System Design — Q&A

**Q39. How would you design a recommendation system for a streaming platform (Netflix)?**
> **Step 1 — Requirements**: latency < 100ms, 200M users, cold start, diversity vs relevance. **Step 2 — Data**: user history (views, ratings, time watched), item features (genre, cast), contextual (time of day, device). **Step 3 — Architecture**: (a) **Candidate generation**: two-tower model (user embedding × item embedding), ANN search → top 1000 items. (b) **Ranking**: gradient boosted trees or deep NN on user-item features → top 20. (c) **Re-ranking**: diversity, freshness, business rules. **Step 4 — Training**: offline batch (weekly), online learning for fresh signals. **Step 5 — Serving**: model store (Redis for embeddings), feature store, A/B testing framework. **Step 6 — Monitoring**: CTR, watch rate, diversity metrics, position bias.

**Q40. How would you design a fraud detection system?**
> **Requirements**: real-time (< 100ms at authorization), low false positive rate (don't decline legit transactions), 99.99% uptime. **Data**: transaction features (amount, merchant, location, time), user history, device fingerprint, velocity features (5 transactions in 1 min?). **Model**: (1) Rules engine (fast, interpretable) → (2) Gradient boosting (XGBoost/LightGBM, handles tabular well) → (3) Graph neural network (catch coordinated fraud rings). **Serving**: feature store (online — Redis, offline — S3), model served via gRPC, response < 50ms. **Challenges**: class imbalance (fraud < 0.1%), concept drift (fraud patterns evolve), adversarial adaptation. **Monitoring**: precision@k, fraud rate, false decline rate, model staleness.

**Q41. What is a feature store and why is it critical?**
> A feature store is a centralized system that stores, computes, and serves features for ML models. Components: (1) **Offline store** (S3/Delta Lake): historical features for training. (2) **Online store** (Redis/DynamoDB): low-latency serving for inference. (3) **Feature registry**: metadata, versioning, lineage. (4) **Transformation pipeline**: batch (Spark) + streaming (Kafka + Flink). Benefits: eliminates training-serving skew (same features both places), feature reuse across teams, point-in-time correct training data (prevents leakage). Tools: Feast, Tecton, Databricks Feature Store, Vertex AI Feature Store.

**Q42. How do you deploy a model for low-latency serving?**
> (1) **Model optimization**: quantization (int8 → 4× smaller), pruning, TorchScript/ONNX export. (2) **Inference server**: Triton Inference Server (supports TensorRT, ONNX, TorchScript, batching). (3) **Batching**: dynamic batching — group concurrent requests, improves GPU utilization. (4) **Caching**: cache embeddings for frequent inputs (Redis). (5) **Hardware**: GPU (A100, T4) for DL; CPU + ONNX for < 10ms tabular models. (6) **Scaling**: horizontal (load balancer + replicas), vertical (larger GPU). (7) **Latency budget**: P50/P95/P99 SLAs — profile each step (preprocessing, inference, postprocessing).

**Q43. How do you detect and handle model drift?**
> **Types**: (1) **Data drift** — input distribution changes (PSI, KS test, MMD). (2) **Concept drift** — relationship between features and target changes. (3) **Prediction drift** — output distribution shifts. **Detection**: (1) Statistical tests on feature distributions vs training baseline. (2) Monitor model metrics (accuracy, AUC) on labeled holdout or production feedback. (3) Compare predicted vs actual labels (when labels arrive with delay). **Handling**: (1) Alert + manual investigation. (2) Automatic retraining trigger when drift score exceeds threshold. (3) Champion-challenger: train new model in shadow, promote when better. Tools: Evidently AI, WhyLogs, Arize, Fiddler.

**Q44. Explain A/B testing for ML models.**
> Split traffic (e.g., 90/10) between champion model (A) and challenger model (B). Measure business metric (CTR, conversion, revenue) not just ML metrics. **Statistical rigor**: calculate required sample size before launch, use two-proportion z-test, set alpha=0.05 and power=0.80. **Pitfalls**: (1) Peeking early — inflate false positive rate. (2) Multiple metrics — Bonferroni correction. (3) Network effects — if users interact, use cluster randomization. (4) Novelty effect — run for full business cycle (2+ weeks). **Shadow mode**: new model runs alongside, predictions logged but not served — compare offline without traffic risk. **Canary**: roll out to 1% → 10% → 50% → 100%.

### 🔧 CHAPTER 6: MLOps — Q&A

**Q45. What is ML model monitoring and what metrics do you track?**
> Three layers: (1) **Infrastructure**: GPU/CPU utilization, memory, latency (P50/P95/P99), error rate, throughput. (2) **Data**: feature drift (PSI, KS test), missing values, schema validation, volume anomalies. (3) **Model**: prediction distribution, confidence scores, business metrics (CTR, revenue), label drift when delayed ground truth arrives. Tools: Prometheus + Grafana (infra), Evidently AI (data/model drift), custom dashboards. Alert thresholds: PSI > 0.2 = high drift, P99 latency > SLA, error rate > 1%.

**Q46. What is the difference between online and offline evaluation?**
> **Offline**: evaluate on held-out test set using ML metrics (AUC, F1, RMSE). Fast, cheap, reproducible. Limitation: doesn't reflect production distribution shifts, user behavior, or position bias. **Online**: A/B test in production, measure actual business metrics (CTR, revenue, engagement). Reflects real user behavior. Expensive, slow, risk of bad user experience. Best practice: offline evaluation to filter candidates → online A/B to confirm winner. Offline lift often ≠ online lift (proxy metric gap).

**Q47. Explain CI/CD for ML. How is it different from software CI/CD?**
> Standard software CI/CD: code → test → build → deploy. ML CI/CD adds: (1) **Data validation**: schema, statistics, distribution checks before training. (2) **Model training**: trigger on new data or schedule — training is part of the pipeline. (3) **Model validation**: compare new model vs baseline on test set, only promote if better. (4) **Model registry**: version, stage (staging/production), artifact storage (MLflow, SageMaker). (5) **Deployment**: canary → production. Tools: MLflow + GitHub Actions, Kubeflow Pipelines, SageMaker Pipelines, Vertex AI Pipelines.

**Q48. How do you version datasets and models?**
> **Datasets**: DVC (Data Version Control) — like Git for data, stores pointers to S3/GCS, tracks data lineage. Delta Lake — ACID transactions, time-travel (query data at any point in time). **Models**: MLflow Model Registry — log model artifact + metrics + params together, stage lifecycle (Staging → Production → Archived). Each model version linked to the dataset version and code commit that produced it. Why it matters: reproduce any past result, audit trail, rollback to previous model version in minutes.

### ⚡ CHAPTER 8: DSA for AI Interviews — Q&A

**Q49. What are the 5 most important DSA patterns for AI engineer interviews?**
> (1) **Two Pointers / Sliding Window** — array/string problems, O(n). (2) **HashMap / HashSet** — O(1) lookups, counting, deduplication. (3) **BFS/DFS** — graph traversal, shortest path, connected components. (4) **Dynamic Programming** — optimal substructure, overlapping subproblems. (5) **Binary Search** — O(log n) search in sorted spaces, also "binary search on answer". AI engineers are also tested on: heap (top-k problems), trie (string search), and occasionally segment trees.

**Q50. How would you find the top-k most frequent elements? (asked at Google)**
> Use a **min-heap of size k**. Count frequencies with a HashMap O(n). Then iterate counts, maintain heap of size k — push if heap size < k, else push and pop if current count > heap[0]. Result in O(n log k). Alternatively: bucket sort by frequency O(n). Python: `collections.Counter(nums).most_common(k)`. Know the heap approach for the interview — shows algorithmic thinking.
